# Probe: Jev for FinFocus recommendation triage (2026-09-28)

Single run of `jev_recommendations_test.go` against `jev-latest` using
`github.com/kataras/jev` v0.1.0. Re-run with:

```bash
go test -run TestJevRecommendations -v -count=1
```

The key is read from `TYPESAFE_API_KEY` or `./.env`; the tests skip without
one.

## Setup

- 19 recommendations copied from FinFocus fixtures
  (`test/fixtures/recommendations/{sample,many}-recommendations.json`) plus 4
  synthetic ones carrying tags (DR standby, HIPAA database, two dev
  resources). These are the fields core keeps after
  `convertProtoRecommendation`: resource ID, description, savings, currency.
  The declared action type was withheld from the model.
- Four questions per request: `safe` (noul), `urgency` (score, 5 levels),
  `action` (choice, 12 action types) and `false_positive` (noul).
- Risk and false-positive labels were fixed in the test file before the
  first call. N is small and the labels are one person's judgement.

## Results

| Check | Result | Verdict |
| --- | --- | --- |
| Auth and models | `GET /v1/models` lists `jev-latest` and `jev-preview`. An invalid key returns 401 with a request ID. | Works as documented |
| Latency | p50 201 ms, p95 305 ms, max 447 ms for a 4-question request | Fast enough for inline use |
| Cost | About 880 input tokens per recommendation, roughly $0.00004 each | Negligible |
| Action classification | 22/22 match the plugin-declared type. `OTHER` (NAT gateway VPC endpoints) became `REFACTOR` at 0.75 confidence | Trivial task, since descriptions restate the action. The forced pick on `OTHER` is a caution |
| False positive from tags | Mean 0.70 with legitimate-reason tags, 0.20 with wasteful tags, 0.31 untagged | Strong, tag-driven signal |
| Risk ordering (`safe`) | Mean P(unsafe) 0.80 for expected-high, 0.58 for expected-low. Spearman 0.41 | Weak. Passes only a loose gap threshold |
| Urgency vs savings | Spearman 0.01 | Urgency ignores savings magnitude |
| Stability, 10 identical calls | `safe` and `false_positive` vary by up to 0.04. `urgency` varies by 0.11 to 0.40 on a 0-4 scale. `action` never flipped | Probabilities are not deterministic |

The tests pass because their thresholds are lenient (risk gap of 0.15, 50%
action agreement). A pass is not a quality result.

## Findings

1. **Use Jev for gating and labelling, not ordering.** The `false_positive`
   question reacted clearly to tags. The `urgency` score clustered between 1.2
   and 2.8, did not track savings, and moved by up to 0.4 across identical
   calls. Keep ranking by savings, deterministically.
2. **Absolute probabilities are unreliable, so use thresholds with a margin.**
   Identical calls differ by a few hundredths. A "flag above 0.7" rule needs
   a dead band, and results should be cached per resource and recommendation.
3. **The `safe` question was badly worded.** It asked about a "production
   workload", so non-prod actions such as stopping dev instances overnight
   scored 0.04 (unsafe). Mean P(safe) was low everywhere (about 0.3), so the
   model leans cautious. Re-test with the environment supplied as state and
   the question about the action alone.
4. **Choice questions need an "unsure" outcome.** `INVESTIGATE` and `OTHER`
   are in the option list, but the model still chose `REFACTOR` for the NAT
   gateway case. Treat confidence below about 0.8 as "route to a human".
5. **Richer state is untested.** Real plugin data has utilization, region and
   costs, all of which core drops today. These fixtures have only a sentence
   of description.

## Client note

`kataras/jev` worked without changes: `ListModels`, `SystemOne` with several
named questions, typed `Noul`, `Score` and `Choice` answers, `*APIError` with
status, request ID and `errors.Is` sentinels. The client's 4-question request
and typed accessors needed no workarounds.
